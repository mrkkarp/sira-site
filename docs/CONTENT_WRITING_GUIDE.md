# Content writing guide — OdudLab product descriptions

How to expand and translate product copy **without inventing facts**. This is
the operating manual for the description rewrite (UK) and the EN/PL
translations. Read it together with:

- `docs/CONTENT_GLOSSARY.md` — the canonical UK→EN→PL term list.
- `_content-audit/facts-audit.md` — the per-product ground-truth manifest
  (generated by `npm run audit:facts`). **This is the only source of facts.**

## 0. The one rule

**Never state a fact the source does not contain.** No invented dimensions,
weights, materials, technologies, certifications, warranties, origin claims,
care instructions, or performance claims. If the facts audit does not list it
for a product, it does not go in that product's copy — in any language.

The brand is premium architectural concrete with a long sales cycle; the goal
is a few high-quality inquiries. Overclaiming to pad a description directly
harms lead quality and trust. Restraint is the correct default.

## 1. What you may draw on, per product

The facts audit gives you, per product, exactly these verifiable inputs:

- `name`, `sku`, `slug`, `shopCategory` (+ `sinkType` / `planterPlacement`).
- `basePriceUah`, and (if present) the custom-colour option + price.
- `heightCm`, `widthCm` — **only for the 16 sinks** that have them.
- `specEntries` — the verbatim "Характеристики" pairs (16 sinks only).
- `leadTimeWeeks`, `mayBeOutOfStock` — only where the source stated them.
- `galleryCount` — how many real photos exist.
- The source free-text `description`.

Anything not in that list for a given product = unknown = omit.

## 2. The 22 products with NO spec block

The audit flags 22 of 38 products (`NO_SPEC_BLOCK`) — all tables, planters,
outdoor pieces, wall panels/art. For these the source states **no dimensions,
no material, no weight**. Their copy may:

- restate the material *only if* the source free-text says it (many say
  "архітектурний бетон");
- describe form, use context, and finish in evocative but non-specific terms;
- **not** give any measurement, weight, or spec value. Not even a range.

If the owner later supplies real specs for these, add them to the source and
re-run the audit — never backfill them from assumption.

## 3. UK description structure

Expand into clearly separated sections (the current
`buildDescriptionSections` only emits an "intro" because the source never
separated them — the rewrite is what creates the real sections):

1. **Intro** — 1–2 sentences: what it is, the material, the feeling. Concrete
   nouns, no superlatives stacked.
2. **Material & make** — architectural concrete; handmade only if stated.
3. **Use & placement** — bathroom / interior / outdoor context. For sinks,
   the real mixer/connection type from specs drives this.
4. **Dimensions & weight** — **sinks only**, straight from `specEntries`.
   Render the table, do not prose-ify approximate weights into exact ones.
5. **Colour & customisation** — the real `Колір` value; mention the custom-
   colour variant + its price only if the product has one.
6. **Lead time** — only if `leadTimeWeeks` is set.

Tone: calm, precise, architectural. Short sentences. No marketing clichés
("perfect", "revolutionary", "the best"). No urgency/scarcity.

## 4. Per-category templates (skeletons, not fill-in-the-facts)

These define *which sections apply*, not what to claim.

- **Sinks (raковини):** all 6 sections. Specs table mandatory (data exists).
  Mixer/connection type is the standout technical detail — surface it.
- **Planters (кашпо):** intro + material + use/placement + colour. No specs
  table (no data). Placement value (`planterPlacement`) may inform section 3.
- **Tables (столи):** intro + material + use + colour. No specs table.
- **Outdoor:** intro + material + use (outdoor durability only if the source
  claims it — most do not) + colour. No specs table.
- **Wall panels / art / modules:** intro + material + interior context +
  colour. No specs table.

## 5. Translation (EN / PL)

- Translate from the finalised UK, using `CONTENT_GLOSSARY.md` verbatim for
  every listed term. Do not re-translate glossary terms ad hoc.
- EN = British spelling (colour, metre, customise). Metric units retained.
- PL = decimal comma; Polish grammatical agreement on units (tygodni, etc.).
- Translation must be **fact-preserving**: no fact added or dropped versus UK.
- **Do not claim a translation is human-verified if it was only machine-
  processed.** Machine-processed drafts are marked `needsReview` (see §6).

## 6. Statuses & review flags

Every piece of generated/translated copy carries review metadata until a human
signs off:

- `needsReview: true` — machine-generated or machine-translated, unverified.
- `factualConflict: true` — the audit flagged a `CONFLICT` for this product;
  a human must resolve which value is correct before publishing.
- `needsOwnerReview: true` — a judgement call only the owner can make (e.g. a
  `PRICE_ANOMALY`, or a product with `NO_SPEC_BLOCK` where copy leans on
  free-text that may be marketing rather than fact).

Do not publish (`editorialStatus: published`) copy that still carries any of
these flags. Draft/needsReview is the safe resting state.

## 7. Backup before any bulk write

Before mutating existing, hand-confirmed copy in Payload, snapshot it first
(export the affected documents to the gitignored `_content-audit/` folder).
Never overwrite manually-confirmed text without that backup. The importer
already refuses to overwrite hand-authored docs (no `legacy.importBatchId`);
the content pipeline must honour the same boundary.

## 8. Workflow

```
npm run audit:facts          # regenerate the ground-truth manifest
# → write/expand UK copy from the manifest, section by section
# → translate to EN/PL using the glossary
# → everything machine-made is needsReview, never published
# → human reviews, clears flags, then publishes in the admin
```

The content-processing script runs in **dry-run / draft** by default: it emits
proposed copy as draft artifacts for review, and only ever writes to Payload as
drafts — publishing stays a human action in the existing admin.
