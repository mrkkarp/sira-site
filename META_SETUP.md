# Meta Pixel + Conversions API

Як підключити Meta до odudlab.com. Код уже готовий — усе, що нижче,
робиться **в інтерфейсах** (Events Manager, GTM, DNS, Vercel) і потребує
доступів, яких немає в репозиторії.

> **Нічого не вигадано.** Ні ID датасету, ні токен, ні код верифікації тут
> не підставлено. У коді є лише «порожні гнізда» — env-змінні, які ви
> заповните реальними значеннями з Events Manager.

---

## Що вже в коді

| Частина | Де | Стан |
| --- | --- | --- |
| Події в `dataLayer` | `src/lib/analytics/events.ts` | Були раніше, не змінювалися по суті |
| `event_id` для дедуплікації | `src/lib/forms/event-id.ts` | Новий — генерується в браузері, їде і в піксель, і на сервер |
| Хешування під Meta (`em`/`ph`/`fn`/`country`) | `src/lib/analytics/meta/user-data.ts` | Новий адаптер; Google-версія (`analytics/user-data.ts`) не чіпалася |
| Відправка на Graph API | `src/lib/analytics/meta/conversions-api.ts` | Новий |
| Виклик з роутів лідів | `lead-endpoint.ts` + `/api/quote` | Через `after()` — після відповіді користувачу |
| Сам піксель у браузері | **у коді немає** | Це тег у GTM — див. крок 3 |

Пікселя як окремого скрипта в `layout` **немає і не повинно бути**. У
кодовій базі рівно один вендорський лоадер — GTM (`NEXT_PUBLIC_GTM_ID`).
Другий скрипт означав би, що кожна подія відправляється двічі, і — на
відміну від дубля «піксель + CAPI» — ці два дублі неможливо
дедуплікувати.

## Крок 1. Обрати датасет (пиксель)

В Events Manager уже є датасет **`582014448861090` «сайт odudlab.com»**.
Важливо розуміти його стан:

- браузерні події в нього йдуть (останні — 03.08.2026);
- **серверних подій не було жодної за весь час** (`server_last_fired_time`
  порожній) — CAPI в Horoshop був налаштований, але нічого не доставляв;
- це піксель **старого сайту на Horoshop**.

Два варіанти, і це рішення власника:

- **Перевикористати той самий датасет.** Зберігається історія й аудиторії,
  але деякий час події старого й нового сайту будуть змішані.
- **Створити новий датасет для нового сайту.** Чиста статистика, але
  навчання алгоритму й аудиторії починаються з нуля.

Обраний ID підставляється в `META_PIXEL_ID`.

## Крок 2. Верифікація домену через DNS TXT

Робиться **не метатегом**. Метатег видно в HTML кожному, хто відкриє код
сторінки; TXT-запис публічно ні на що не вказує.

1. Business Manager → **Налаштування компанії** (Business Settings) →
   **Безпека бренду** → **Домени**.
2. **Додати** → `odudlab.com`.
3. Обрати спосіб **DNS TXT record**. Meta покаже рядок виду
   `facebook-domain-verification=<токен>`.
4. У DNS-провайдера домену `odudlab.com` додати запис:
   - тип: `TXT`
   - ім'я/host: `@` (корінь домену)
   - значення: рядок з кроку 3 повністю
5. Зачекати поширення DNS (зазвичай хвилини, іноді до доби) і натиснути
   **Verify**.
6. Після верифікації прив'язати датасет до домену в тому ж розділі.

## Крок 3. Піксель — тегом у GTM

### 3.1. Змінні dataLayer

Створити **Variables → New → Data Layer Variable** для кожного імені:

`event_id`, `value`, `currency`, `items`, `transaction_id`, `location`,
`channel`

Іменувати їх послідовно, напр. `DL - event_id`.

> Кожна подія в коді явно **очищає** всі параметри, яких сама не несе
> (`EVENT_PARAMETERS` у `data-layer.ts`). Без цього GTM тягнув би
> `value: 19600` від запиту прорахунку на наступний клік по телефону, і
> Smart Bidding вчився б, що тап по номеру коштує 19 600 ₴.

### 3.2. Базовий тег

**Tag → Custom HTML**, назва `Meta Pixel — base`:

```html
<script>

n.callMethod.apply(n,arguments):n.queue.push(arguments)};if(!f._fbq)f._fbq=n;
n.push=n;n.loaded=!0;n.version='2.0';n.queue=[];t=b.createElement(e);t.async=!0;

```

- Тригер: **All Pages**.
- **Advanced Settings → Consent Settings → Require additional consent**:
  `ad_storage`, `ad_user_data`, `ad_personalization`, `analytics_storage`.
  Сайт уже має Consent Mode v2 (`src/lib/analytics/consent-mode.ts`) з
  denied за замовчуванням; без цієї галочки тег проігнорує відмову
  відвідувача.

### 3.3. Тригери та теги подій

Для кожної події — **Trigger → Custom Event** з точною назвою події
(`quote_request` тощо), і **Custom HTML** тег:

| Подія в коді | Тег Meta | `event_id` |
| --- | --- | --- |
| `quote_request` | `Lead` | так |
| `designer_inquiry` | `Lead` | так |
| `contact_submit` | `Lead` | так |
| `sample_request` | `Lead` | так |
| `phone_click` | `Contact` | ні |
| `messenger_click` | `Contact` | ні |
| `add_to_cart` | `AddToCart` | ні |
| `begin_checkout` | `InitiateCheckout` | ні |
| `purchase` | `Purchase` | `transaction_id` |

Чотири події лідів (перші в таблиці) — ті самі, які сервер дублює через
CAPI, тому їм **обов'язково** потрібен `eventID`:

```html
<script>
  fbq('track', 'Lead', {
    value: {{DL - value}},
    currency: {{DL - currency}},
    content_name: 'contact_submit'
  }, { eventID: {{DL - event_id}} });
</script>
```

`Contact`, `AddToCart` та `InitiateCheckout` серверної копії не мають —
там `eventID` не потрібен, піксель згенерує свій.

Для `Purchase` варто передати `{ eventID: {{DL - transaction_id}} }` —
тоді перезавантаження сторінки «замовлення прийнято» не порахується
другою покупкою.

> `value` наразі буде порожнім для `contact_submit`, `designer_inquiry`,
> `phone_click` і `messenger_click` — див. крок 5.

## Крок 4. Conversions API — змінні оточення

Токен генерується в Events Manager → ваш датасет → **Налаштування** →
**Conversions API** → **Створити токен доступу**.

Це **ключ на запис** до даних рекламного акаунта. Його не можна
комітити, не можна писати в лог і не можна ставити з префіксом
`NEXT_PUBLIC_` (це вшило б його в JavaScript-бандл). Додайте його у
Vercel самостійно — у репозиторії його бути не повинно:

```
npx vercel env add META_PIXEL_ID production
npx vercel env add META_CAPI_ACCESS_TOKEN production
```

Локально — у `.env.local` (він у `.gitignore`). Повний опис усіх змінних
— у `.env.example`, блок «Meta».

Поки `META_PIXEL_ID` або `META_CAPI_ACCESS_TOKEN` не задані, серверні
події просто не відправляються: жодного запиту, жодної помилки.

## Крок 5. Вартість ліда — потрібне рішення власника

`NEXT_PUBLIC_LEAD_VALUE_UAH` досі **не задана**, і числа тут не буде
вигадано.

- Ліди, прив'язані до товару (прорахунок або зразок зі сторінки товару),
  уже несуть **реальну ціну обраного варіанта** — і в пікселі, і на
  сервері, де вона перечитується з каталогу, а не береться з тіла
  запиту.
- Решта — звернення дизайнерів, повідомлення з форми контактів, тапи по
  телефону й месенджерах — не мають товару за собою. Їх вартість = ваш
  середній чек × конверсія в продаж. Обидва числа знає тільки бізнес.

Поки змінна порожня, ці події рахуються як конверсії, але без `value`,
тож value-based bidding не має що оптимізувати.

## Крок 6. Перевірка

### 6.1. Test Events

1. Events Manager → датасет → **Test Events**, скопіювати код `TEST#####`.
2. Тимчасово задати `META_CAPI_TEST_EVENT_CODE` цим кодом.
3. Відправити тестову заявку через форму на сайті.
4. У вкладці Test Events має з'явитися **дві** події `Lead` — `Browser`
   і `Server` — які **склеюються в одну** з позначкою **Deduplicated**.
   - Якщо позначки немає і подій дві окремі — `event_id` не збігається.
     Перевірити, що змінна `DL - event_id` у GTM названа саме `event_id`
     і що тег читає її.
   - Якщо є лише `Browser` — CAPI не налаштований або токен неправильний.
     Дивитись логи функції у Vercel: помилка пишеться як
     `[meta] Conversions API rejected Lead: …` (токен у логах
     замінюється на `[redacted]`).
5. **Прибрати `META_CAPI_TEST_EVENT_CODE`.** Поки він заданий, події не
   рахуються як конверсії — і це не видно ніяк, крім того, що кампанія
   тижнями вчиться ні на чому.

### 6.2. Event Match Quality

Events Manager → датасет → подія `Lead` → **Event Match Quality**.
Оцінка рахується за кілька днів реальних подій, не миттєво.

Що відправляється й чому:

- `em` — email, коли форма його зібрала (у формі контактів необов'язковий).
- `ph` — телефон у E.164 **без плюса** (Meta вимагає саме так; Google —
  з плюсом, тому це окремий адаптер, а не правка спільної функції).
- `fn` — ім'я, перший токен, лише літери.
- `country` — тільки якщо номер розпізнався як український (`+380`).
- `fbp` / `fbc` — cookies пікселя. `fbc` — найсильніший сигнал: це точна
  прив'язка до конкретного кліку по рекламі.
- `client_ip_address`, `client_user_agent` — з самого запиту.

Свідомо **не** відправляється:

- `ct` (місто) — жодна форма на сайті його не питає. Вивести з префікса
  номера чи з IP означало б вгадати; неправильний хеш не збігається ні з
  ким **і** псує саму оцінку EMQ, яка мала б про це попередити.
- `ln` (прізвище) — у полі «Ім'я» другим словом часто йде по батькові.
- `external_id` — у браузері немає стабільного ідентифікатора, з яким
  Meta могла б це зіставити.

## Як це оцінювати

Не за CTR, CPM чи ROAS. Ніша — преміальний архітектурний бетон із довгим
циклом ухвалення рішення; десять звернень від людей з проєктом кращі за
сто дешевих. У подіях `quote_request` і `designer_inquiry` є параметри
`projectType` і `timeline` саме для того, щоб це питання можна було
поставити в звіті, а не лише «скільки лідів».

Окремо варто пам'ятати: Meta не може сама сказати, чи лід був якісним.
Без CRM або офлайн-конверсій це знає тільки майстерня.
